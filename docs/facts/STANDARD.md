# Facts 事实规范

版本：1.0

本规范定义项目如何维护“系统当前真实是什么”。它与具体技术栈、研发流程和发布工具无关，可随 `docs/facts/` 一起放入任意项目。

## 1. 事实的判定

一条内容只有同时满足以下条件，才可以写成已确认事实：

- 描述的是当前状态，而不是未来意图、建议或执行步骤。
- 作用范围明确，例如整个项目、某个服务、某个应用或某个环境。
- 有可复核来源，例如代码、测试、配置、schema、持续集成、命令输出、运行结果、官方文档或用户明确提供的证据。
- 表述没有超出来源实际证明的范围。

事实最少应能回答：主张是什么、适用于哪里、依据是什么、何时确认。可以使用表格、列表或紧邻正文的来源说明，不强制一种固定格式。

## 2. 事实状态

标记一条事实的确认状态时，使用以下状态，不自行发明近义状态。业务对象状态、部署阶段等项目自身的领域值不受本表约束：

| 状态 | 含义 |
| --- | --- |
| `已确认` | 当前证据足以支持该主张。 |
| `待定` | 尚无足够证据，或还没有完成核验。 |
| `冲突` | 两个或多个当前来源给出不一致结论，尚未消解。 |
| `不适用` | 该分类或能力不属于本项目，且已经写明判断依据。 |

历史事实不作为第五种状态长期堆积。事实失效后，更新当前正文；变化历史交给版本控制。仍影响当前判断的旧事实，可以作为冲突或约束的来源简要保留。

## 3. 证据使用

证据是否优先取决于主张类型，不使用一套脱离语境的固定排序：

- 实现和结构事实，以当前代码、配置、schema 和生成物为主要来源。
- 行为事实，以当前测试、可复现命令和运行结果为主要来源。
- 部署和外部平台事实，以目标环境的读取结果、平台状态和官方文档为主要来源。
- 业务语义，以已实现的不变量、正式业务材料和用户明确确认的规则为来源。
- 命令事实，必须由项目脚本、持续集成、项目文档或官方工具文档确认，并记录实际运行结果。

当代码、测试、文档、运行环境或用户证据互相冲突时，不凭印象挑选一个结论。将状态标为“冲突”，记录双方证据和下一步核验方式。

搜索结果、模型输出、旧对话摘要和未经读取的二手描述只能作为定位线索，不能单独作为已确认事实。

## 4. 读取顺序

处理项目事实时按以下顺序读取：

1. 项目根目录及当前路径适用的 `AGENTS.md`。
2. `docs/facts/AGENTS.md` 和本规范。
3. `docs/facts/current-system.md`。
4. `current-system.md` 索引指向的相关分类文件和范围文件。
5. 支撑本次主张的代码、测试、配置、命令或运行结果。

不能只读 `current-system.md` 就对分类事实作完整结论。

## 5. 写入顺序

写入任何事实前依次执行：

1. 把待写内容改写成可验证的当前状态主张。
2. 确定作用范围和证据来源。
3. 选择唯一主文件。
4. 检查其他事实文件是否已有重复或冲突表述。
5. 写入当前事实、来源和最近确认信息；证据不足则写“待定”。
6. 更新 `current-system.md` 的索引、范围映射、刷新记录或冲突入口。
7. 检查链接、路径、术语、状态和来源是否仍然一致。

不要因为刚完成一次修改，就把预期结果直接写成事实。必须先取得能够证明该结果的当前证据。

## 6. 标准分类

| 文件 | 唯一职责 |
| --- | --- |
| `current-system.md` | 项目状态摘要、事实索引、技术栈范围、范围映射、最大待确认事项、刷新记录和冲突入口。 |
| `architecture.md` | 技术栈、目录与模块边界、运行方式、共享契约位置和主要数据流。 |
| `product-domain.md` | 跨范围成立的业务对象、规则、状态语义、权限语义、术语和业务不变量。 |
| `ui-style.md` | 跨页面成立的视觉方向、组件约束、交互原则和界面不变量。 |
| `integrations.md` | 外部服务商、第三方接口、账号能力、假实现、沙箱、回调和网络边界。 |
| `deployment.md` | 本地及远端环境、数据库、迁移、备份、运维、监控和回滚约束。 |
| `verified-commands.md` | 已确认命令、适用范围、来源、最近运行时间和结果。 |
| `scopes/<稳定范围名>.md` | 某个子项目、服务、应用或共享包如何实现、使用和验证横向事实。 |

`current-system.md` 是总览和索引，不承载分类事实正文。同一事实只在一个主文件完整描述，其他文件只记录承载关系或链接。

## 7. 范围与扩展

普通单项目可以只使用横向分类文件。出现以下任一情况时，应创建 `scopes/<范围名>.md`：

- 单仓包含多个项目、服务或应用。
- 不同目录使用不同技术栈或验证命令。
- 同一全局规则在不同范围有不同实现或验证状态。
- 某个共享包或契约具有独立边界。

范围名必须稳定，不能使用变更编号、人员名、临时分支名或一次性任务名。

标准分类无法承载一个长期、独立的事实领域时，可以新增 `docs/facts/<领域名>.md`。新增文件必须职责单一、在 `current-system.md` 登记，并避免与现有文件重复。例如平台专项事实可以独立成文件，但该平台的部署、命令和范围实现仍应分别链接到现有主文件。

## 8. 全局规则与范围实现

- 规则本身写入横向分类文件。
- 某个项目、应用或服务如何实现、展示、调用、存储、校验或验证该规则，写入对应范围文件。
- 共享契约如何表达规则，写入共享契约范围文件，或在 `architecture.md` 记录契约边界。
- 不在范围文件里重新定义一份全局业务规则。

## 9. 命令事实

命令只有在以下信息齐全时才能标为“已确认”：

- 完整命令文本。
- 适用目录、服务和环境。
- 命令来源。
- 最近运行时间和结果。

仅在 README 或官方文档中看到、但未在本项目运行过的命令，可以记录来源，但最近结果仍为“待定”。不得依据技术栈习惯补写默认命令。

## 10. 冲突、刷新与过期

- 发现冲突时，在 `current-system.md` 登记主张、冲突证据和处理状态，并在相关主文件保留必要上下文。
- 代码、配置、schema、依赖、环境或外部平台变化后，只重新核验受影响事实。
- “最近事实刷新”必须说明刷新范围、时间、依据和结果，不能只写一个没有范围的日期。
- 已确认事实长期未复核不自动变成错误，但在依赖它作决策前必须评估漂移风险并按需刷新。
- 不保留与当前状态无关的流水账；历史由 Git 保存。

## 11. 敏感信息

Facts 可以记录凭据来自哪个安全存储、由哪个环境变量或平台能力提供，但不得记录密钥、令牌、密码、Cookie、私钥或完整连接串。必要时只记录经过脱敏的标识和获取边界。

## 12. 禁止事项

- 不得按变更编号创建 `docs/facts/chg-*`。
- 不得把未来计划、愿望、建议、执行步骤或尚未实现的设计写成当前事实。
- 不得把截图、视频、跟踪文件、原始日志、覆盖率网页或完整测试报告存入 Facts。
- 不得把检索结果或模型推断直接升级为事实。
- 不得用旧文档覆盖更新的代码、测试、配置、运行结果或平台读取结果。
- 不得发明未确认的命令、环境变量、接口、字段、状态、部署方式或外部服务能力。
- 不得为了目录看起来完整而创建没有实际职责的范围文件或分类文件。

## 13. 最小完整性检查

一次 Facts 初始化或更新完成前，至少确认：

- `current-system.md` 的索引与实际文件一致。
- 每条新增已确认事实都有可复核来源和明确范围。
- “待定”“冲突”“不适用”没有被写成已完成状态。
- 分类事实没有长期堆积在 `current-system.md`。
- 没有同一事实的多份完整正文。
- 没有残留其他项目的路径、服务名、命令或环境信息。
- 没有明文敏感信息。
- 文件引用和相对路径有效。
